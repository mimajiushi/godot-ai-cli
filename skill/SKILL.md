# godot-ai-cli

Drive a live Godot editor through the `godot-ai-cli` binary. One `launch` installs the bundled `godot_ai` plugin into the project, starts the local daemon (HTTP 8000 / plugin WebSocket 9500 by default), opens the editor, and waits for the plugin handshake; afterwards every editor operation is a subcommand printing one English JSON object.

## Inputs to collect

- Project directory containing `project.godot` (required by `launch`; ask when ambiguous).
- Headed vs `--headless`: headless is for CI-style JSON operations only — the viewport renders nothing, so screenshots fail structured (see Failure handling). Anything visual needs a windowed editor.
- Godot binary path only when auto-detection finds nothing or the wrong one (`--godot` flag, `GODOT_BIN` env, or a one-time `godot-ai-cli godot use <path>` that persists it).
- Custom ports only when 8000/9500 are occupied (see Failure handling).

## Procedure

1. CLI present? Run `godot-ai-cli -v`. If missing, install with the bundled script for the current platform: `bash scripts/install.sh` (linux/darwin/Git-Bash) or `powershell -ExecutionPolicy Bypass -File scripts/install.ps1` (Windows). The script resolves the latest GitHub release of `mimajiushi/godot-ai-cli`, downloads `godot-ai-cli-<ver>-<os>-<arch>.zip` plus the release checksums, verifies SHA256, installs, and prints the verified version. When the repo has no published release yet it says so and exits — then build from source instead (`go build -o godot-ai-cli.exe ./cmd/godot-ai-cli` in a clone; needs Go). Overwriting an existing install is the documented behavior; the version check after install is what proves success. If the CLI is already installed and the task is upgrading it, do NOT re-run the install script — use `godot-ai-cli update`: it queries GitHub Releases (prereleases count), verifies SHA256 against the release checksums, and replaces the binary in place after an interactive confirmation. `--yes` skips the prompt; with no terminal at all (agent/CI pipes) the update is declined instead — the result is `cancelled` plus the release details and a hint, so re-run `godot-ai-cli update --yes` to apply. On Windows the running exe is renamed aside as `.old` and removed on next startup. When the update result carries `docs_hint`, the op surface changed (the hint lists the added/removed ops): re-sync the docs — `godot-ai-cli commands --format md > references/commands.md` regenerates this catalog mechanically, then refresh the ops counts in SKILL.md (frontmatter line and the Need/Read table) to match `godot-ai-cli -v`.
2. Version compatibility (check before launching, and warn the user when mismatched): `godot-ai-cli -v` prints BOTH contracts — `supported Godot:` (4.5+, 4.7+ recommended) and `bundled plugin: godot-ai vX.Y.Z` (the upstream godot-ai release the embedded editor plugin was forked from; the handshake requires an editor plugin with the SAME major.minor as the bundled one — a patch-level drift like 3.2.6-plugin ↔ 3.2.7-daemon is ACCEPTED and flagged `plugin_stale`, only a minor/major mismatch is refused, and `plugin install` aligns a project to the bundled version). Then run `godot-ai-cli godot detect` — it probes `GODOT_BIN`, the default saved by `godot use`, PATH, and the conventional per-OS install dirs, the same sources launch resolves from (launch adds the `--godot` flag on top). Empty `candidates` → have the user install Godot 4.7+, supply `--godot`, or persist a custom-location binary once with `godot-ai-cli godot use <path>` (saved in the user config dir, so no per-shell `GODOT_BIN`). Below 4.5, launch fails with `GODOT_UNSUPPORTED`; 4.5–4.6 works — warn the user that 4.7+ is recommended; 5.x launches with an untested-major warning in the payload. If the project already has an `addons/godot_ai` whose plugin.cfg version differs from the bundled one, say so and run `godot-ai-cli plugin install --project <dir>`: a patch-only drift still connects (the session shows `plugin_stale: true` in `status`/`session list` with an align note, and `launch` reusing such a session adds the same warning — the running editor keeps its OLD plugin code until restarted), while a major/minor mismatch makes both plugin and daemon refuse the handshake outright.
3. Launch: `godot-ai-cli launch --project <dir>` and wait for `{"status":"ready",...}`. Add `--headless` for CI, `--wait 90` on slow machines, `--http-port N --ws-port M` when defaults are taken. launch spawns the backend daemon itself — `godot-ai-cli serve` runs the same daemon in the foreground and is only for debugging daemon startup. Before spawning the editor, launch writes the daemon ports into `<project>/.godot/godot_ai_ports.json` (default ports too; the plugin resolves ports as project file > EditorSettings > default) — the global EditorSettings is never touched, so several daemons on different ports coexist without cross-wiring projects. Re-running launch while a session for THE SAME project is live reuses that connected editor instead of opening a second one; launching a DIFFERENT project opens its editor as an additional session on the same daemon and pins it active. If an editor for the SAME project is already connected to ANOTHER daemon (e.g. you opened the editor by hand while an old daemon was up), launch fails with `EDITOR_ALREADY_OPEN` instead of double-opening — join that daemon with `--http-port <port>` (or migrate with `--upgrade-daemon`); `--force-spawn` opens a second editor anyway at scene-lock/save-overwrite risk. When several projects share one daemon, ops go to the ACTIVE session — pin another project with `session activate <id>` or an op's `--session` flag (`session list` shows who is connected).
4. Operate via the domain subcommands. The full catalog with every flag, timeout, and write gate is in references/commands.md — or ask the binary: `godot-ai-cli commands` (text), `godot-ai-cli commands --json --domain node` (includes `cli_flags` and `response` per op), `godot-ai-cli commands --format md` (regenerates references/commands.md), `godot-ai-cli <domain> <op> -h`. The CLI's own non-op commands (`launch`, `stop`, `status`, `update`, `godot detect`, `godot use`, `plugin install`, `version`) are NOT in that op catalog — they are listed at the top of references/commands.md and in `godot-ai-cli -h`; check there before hand-rolling a workflow the CLI already covers. Node paths are scene-root-absolute (`/Root/Child`, `""` = the scene root) — the conventions section of references/commands.md has the details. Assigning a NODE to a property (the editor-inspector "drag a node onto the slot" case) goes through the `$node` reference encoding: `node set-property --path /Root/Player --property target --value '{"$node":"../Sprite2D"}'` — or the `--node-ref ../Sprite2D` shorthand — where the path resolves RELATIVE TO THE TARGET NODE (`../Sprite2D` on `/Root/Player` = `/Root/Sprite2D`; a scene-root-absolute `/Root/Sprite2D` works too). Follow with `scene save` and the .tscn serializes exactly like the manual drag (NodePath + `node_paths` entry); an unresolvable reference fails with `NODE_NOT_FOUND`, a malformed one with `INVALID_PARAMS`. Use `call <plugin_command> --params '<json>'` for anything without a typed subcommand, `custom list` / `custom invoke` for third-party tools registered in the editor, and `batch execute --file ops.json` to run several plugin commands atomically (rollback on first error). Canonical end-to-end recipes are in references/workflows.md.
5. Verify after each mutation batch, not once at the end: `scene get-hierarchy` for structure, `node get-properties --path <p>` for values, `logs read --source plugin|game|editor` for errors, `editor state` for readiness and play state. Filter logs server-side instead of post-processing JSON yourself: `logs read --level error --grep <substr> --tail 20` (filtered responses add `matched_count`; `--since-cursor <n>` + the response's `next_cursor` give incremental reads). Runtime probes are one call, not two: `editor eval --code '...'` returns the code's explicit `return` value as `result`, and `--echo-prints` adds the eval's own print lines as `prints`. Screenshot checkpoints (`editor screenshot`) require the windowed editor. Screenshots arrive as base64 data URIs — save them with `editor screenshot --out <file.png>` (stdout then stays small, the file is viewable with image-reading tools) and verify rendered pixels in one step with `--assert '#RRGGBB@x,y'` (+ `--tolerance <n>`; a mismatch exits 1 as `PIXEL_ASSERT_FAILED` with the actual colors in `data.samples`). The default capture is capped at 640 px on the longest edge — too small to eyeball pixel-art frames; add `--full-res` for the source resolution, or `--region 'x,y,w,h'` to crop in source-image pixels (crop first, cap applies after). To verify per-frame animation content or projectile/particle motion in ONE call, use `editor record --frames N --out-dir <dir>` (frame-aligned burst, one readback per game frame) or `--duration <sec> --fps <n> --format gif --out run.gif`. To check how a sprite sheet is REALLY cut before slicing SpriteFrames, use the LOCAL `image grid-detect --path <png>` (alpha-cluster analysis → suggested cell/frames) — never assume width÷cell arithmetic. For texture color analysis use the LOCAL `image palette` (dominant colors, `--grid WxH` for TileSet atlases) and `image probe` (pixel sampling of a saved file) — neither needs the editor, Python, or any other runtime. A saved frame too small to eyeball gets a nearest-neighbor zoom from the LOCAL `image view --path <png> --scale N --out <big.png>` (`--region x,y,w,h` crops first) — pixel art stays crisp. To verify collision-shape fit visually, `game debug-draw --collisions on` enables the engine's debug outlines and they ARE visible in `editor screenshot --source game` / `editor record` captures (beware a `stale_frame` capture from a frozen game). To author 2D sprite animations as maintainable .tres resources, use `resource spriteframes-from-sheet` (batch-build animations from a sheet grid, e.g. `--cell 32x32 --rows "0:idle,1:walk"`) plus `resource spriteframes-add-animation` / `spriteframes-add-frame` for per-frame edits; inspect with `resource spriteframes-list-frames` and exchange two animations' frame lists with `resource spriteframes-swap-frames`. For TileMapLayer inspection without opening the scene, the LOCAL `tilemap dump --scene <tscn> [--layer <name>]` decodes tile_map_data cells straight from the .tscn text and `tilemap render --scene <tscn> [--layer <name>] --out map.png` composites one layer to a PNG (layers are not stacked; alternative != 0 tiles draw as 0 with a stderr note). TileSet collision authoring is `tileset add-physics-layer` (collision layer/mask bits) then `tileset set-tile-collision --atlas-coords x,y --points "x,y x,y ..."`. If an eval breaks the game loop (debugger break), it now auto-resumes; a self-inflicted break elsewhere recovers with `project continue`. When eval reports the main loop not advancing because the game window lost focus, `project focus` raises it — during a break it may not take effect, so `project continue` first.
6. Stop when done: `godot-ai-cli stop` (no `--http-port` needed — launch recorded the ports; pass it only to stop a daemon other than the last launched). (`project stop` is a different, narrower op: it only stops the RUNNING GAME and leaves the editor open.) A full `stop` now asks ONLY CLI-launched editor sessions to quit (one pinned quit per session — an unpinned quit would only reach the active one) and deliberately KEEPS editors the user opened manually: the daemon tags each session's `origin` from the plugin handshake (`launched_by` = `"cli"` when `launch` spawned the editor, `"user"` otherwise — plugins older than 3.2.7 send no field and always count as `"user"`, so they are never auto-quit). Kept sessions come back in the stop payload's `kept_sessions` array, and `status` marks them with a per-session `note`. Use `stop --all` when every connected session must quit (the pre-3.2.7 behavior). When several projects share the daemon and only one is finished, use `stop --session <id>`: it quits exactly that editor (regardless of origin) and leaves the daemon and the other sessions running; its result is `session_stopped` once the session actually left, or `quit_requested` (with a warning) when the editor stayed connected — treat the latter as "not stopped yet", not as success. The daemon itself always shuts down, stop then removes each session project's port pin (`.godot/godot_ai_ports.json`, only while it still points at the stopped daemon — reported as `project_ports_cleared`), and — when a PRE-3.2.9 launch had overridden the plugin ports in the user's global EditorSettings — stop restores those byte-identically; the payload then carries `settings_restored: true` (a kept editor that is still running defers the restore with a warning, because its exit-time settings write would undo it).

## Updating the whole bundle (CLI + skill + plugin — always together)

The CLI binary, this skill, and the editor plugin are ONE release unit: every GitHub release of `mimajiushi/godot-ai-cli` ships all three. The handshake tolerates a patch-level plugin drift (accepted, flagged `plugin_stale`) but refuses a minor/major mismatch — a half-updated set still fails loudly once versions drift beyond the patch segment, and a stale plugin never fails silently (status/launch warn). When updating, always update the complete set, in this order:

1. **CLI binary**: `godot-ai-cli update` (NOT the install script — that is for first install only). `--yes` when there is no TTY. The result's `docs_hint` lists added/removed ops and means the reference docs must be re-synced (step 1 of the Procedure).
2. **Skill files (this directory)**: download `godot-ai-skill.zip` from the SAME release tag the CLI now reports (`godot-ai-cli -v`) and replace EVERY installed copy of the skill — delete each old skill directory first (stale leftovers survive a naive copy), then unpack, then verify `SKILL.md` exists at each location. Mixed old-skill + new-CLI is exactly the failure mode this ordering prevents: an outdated skill teaches removed ops and stale workflows.
3. **Editor plugin (per project)**: the plugin is vendored inside the CLI — no separate download. Run `godot-ai-cli plugin install --project <dir>` for each project you work in, then fully QUIT and relaunch the editor (a real process restart; `filesystem scan` / `reload-plugin` keep running stale plugin code, especially through symlinked addons). The handshake then proves alignment: `godot-ai-cli -v` prints `bundled plugin: godot-ai vX.Y.Z`; a project plugin that drifted at patch level connects but is flagged `plugin_stale` (status note + launch warning — install and restart to pick up new ops), and a minor/major mismatch refuses the handshake.

Skip any of the three and the set is inconsistent — never update "just the binary".

## Output contract

- Success: one JSON object on stdout, exit 0. `launch` ends with `{"status":"ready","session_id":...,"godot_version":...,"warnings":[...]}` — surface non-empty `warnings` to the user.
- Failure: `{"status":"error","error":{"code","message","data"}}` on stdout, exit 1. Route recovery on `error.code` and `error.data.sub_code`; honor `error.data.retryable` before blind retries.
- `--pretty` (placed before the subcommand) indents JSON when showing output to humans.
- A task is finished only when: mutations were read back via verify ops, a running game was stopped (`project stop`), the daemon was stopped and the CLI-launched editors quit (`stop` — user-opened editors are kept on purpose and listed as `kept_sessions`; use `stop --all` when they must go too), and port pins are confirmed gone (`project_ports_cleared` / `settings_restored` in the stop payload, or `status` showing `ports_override_active: false`).
- `status` also reports `known_daemons`: EVERY recorded daemon on this machine probed live (running ones with version/ports/session projects, dead records with `running:false`), so a multi-daemon setup (old CLI versions, parallel ports) is visible in one call.

## Failure handling

Route on `error.code`; the full taxonomy with per-code recovery lives in references/troubleshooting.md. The load-bearing cases:

- `FOREIGN_SERVER` at launch: port 8000/9500 is held by another process — commonly the upstream Python godot-ai server. Do not kill it. Re-launch on free ports, e.g. `--http-port 18000 --ws-port 19500`. launch records the ports (last-daemon.json in the user cache dir), so later commands — including `stop` — find the daemon WITHOUT repeating `--http-port`; the explicit flag still wins when given, and resolution falls back to port 8000 when the recorded port is dead. (Ops only take `--http-port`; the WS port is chosen once at launch and carried by the daemon.)
- `DAEMON_MISMATCH`: the daemon on the requested port has a different WS port or an INCOMPATIBLE version (major.minor differs — a patch drift is adopted with a stale warning, not an error). Three ways out: ① when `error.data.same_version_daemon` is present, a compatible daemon is already running — re-launch with `--http-port <that port>`; ② re-run with `--upgrade-daemon` — the old daemon shuts down WITHOUT quitting any connected editor (compatible plugins reconnect to the new daemon automatically; incompatible ones need `plugin install` + an editor restart); ③ `stop --http-port <N>` (quits CLI-launched editors) and launch again.
- `EDITOR_ALREADY_OPEN`: an editor for THIS project is already connected to another daemon (`data.daemon_http_port` / `data.daemon_version` / `data.session_id` / `data.editor_pid`). Re-run with `--http-port <daemon_http_port>` to reuse that session; if the versions are incompatible, `plugin install --project <dir>` + restart that editor first, or `--upgrade-daemon` to migrate. `--force-spawn` opens a second editor anyway — scene file locks and saves can overwrite each other, so prefer reuse.
- `SETTINGS_OVERRIDE_ACTIVE` (legacy, pre-3.2.9 launches only): a previous custom-port session's overrides are still live in the shared global EditorSettings. Run `stop --http-port <active_http_port>` (named in `error.data`) first, then re-launch. Current launches never touch the global EditorSettings (ports are pinned per project), so this no longer blocks new launches.
- `EDITOR_NOT_READY`: read `data.sub_code`. `EDITOR_IMPORTING` — retryable, the daemon already held the write ~8s; retry once. `EDITOR_PLAYING` — run `project stop` first. `EDITOR_NO_SCENE` — `scene open` first. `EDITOR_GAME_NOT_RUNNING` — `project run` first. `EDITOR_VIEWPORT_EMPTY` — headless viewport; not retryable, relaunch windowed.
- `PLUGIN_DISCONNECTED` / `TRANSPORT_TIMEOUT`: transient transport faults; retry once, then inspect `status`.
- `LAUNCH_TIMEOUT`: the editor is usually still starting — check `status` for a session before retrying with a larger `--wait`.
- `test run` reports mass phantom failures with a `scene_warning` field: scene-dependent suites assume the project's main scene is the edited scene — `scene open` it first, then re-run (see references/workflows.md).

## Windows (win32) platform notes

- The Windows binary is `godot-ai-cli.exe`; `scripts/install.ps1` installs to `%LOCALAPPDATA%\Programs\godot-ai-cli` and appends that directory to the user PATH via `[Environment]::SetEnvironmentVariable(..., 'User')`. New terminals inherit it; the current shell does not — invoke the full path until a new shell is opened.
- Under Git Bash prefer forward slashes inside flag values (`--project C:/games/rpg`, `--godot D:/tools/godot.exe`).
- Git Bash (MSYS) rewrites flag values that start with `/`: `--parent-path /Root/Child` arrives as `C:/Program Files/Git/Root/Child` and fails with `NODE_NOT_FOUND`. Either prefix the command with `MSYS_NO_PATHCONV=1` (e.g. `MSYS_NO_PATHCONV=1 godot-ai-cli node create --parent-path /Level1 ...`) or use the `""`/relative forms (`--parent-path ""` targets the scene root). PowerShell and cmd.exe are unaffected.
- JSON quoting: PowerShell accepts `--params '{"a":1}'` with single quotes; cmd.exe needs double quotes with inner ones escaped. For larger payloads (`batch execute`, `ui build-layout`, `game input-sequence`) write the JSON to a file and use `--file`/file-reading flags instead of fighting quoting.
- `scripts/install.sh` also runs under Git Bash; when `sha256sum` is absent it falls back to `certutil -hashfile` (and to `shasum -a 256` on macOS).
